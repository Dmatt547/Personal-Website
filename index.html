Bullion Tracker

Vanilla JS (ES modules) · Firebase · Chart.js · Netlify

JavaScriptFirebaseChart.jsNetlify

Overview

A web app for tracking a gold and silver bullion portfolio in AUD. It pulls live spot prices, works out cost basis and unrealised profit/loss, and keeps your holdings synced across every device you sign in on. Built with plain JavaScript ES modules: no framework and no build step.

My role

I designed and built the whole thing end to end on my own: the front-end, the data and auth layer, the live price integration and the deployment pipeline.

What I built

  • Live spot prices from a metals API, converted USD→AUD with a live FX rate and auto-refreshed every 5 minutes
  • Google sign-in with real-time cross-device sync via Firebase Auth + Firestore, falling back to local storage when signed out or offline
  • Cost-basis and break-even maths with blended average $/oz and profit/loss per metal
  • Charts for allocation, cost vs current value, and portfolio value over time (Chart.js)
  • CSV import/export, inline editing, and oz/gram weight entry stored canonically in troy ounces
  • Continuous deployment to Netlify with CI on GitHub Actions

Outcome

Shipped a live, production app I use myself, and got hands-on with authentication, real-time databases, third-party API integration and CI/CD, all without reaching for a framework.

Job Tracker

React 18 + TypeScript · Supabase (Postgres) · Scheduled AI agent · Node · Netlify

ReactTypeScriptSupabaseTailwindAutomationGmail APINetlify

Overview

A job application tracker in two halves: a React web app backed by Postgres, and a scheduled AI agent that reads my inbox and the job boards every evening, works out what has changed and writes it to a seed file, which a second scheduled job then pushes into the database. It currently holds 106 roles across five pipeline stages. I built it because the spreadsheet I was using could tell me what I had applied for, but not what I needed to do today.

My role

Solo project, built end to end: the agent brief, the sync bridge, the database and auth layer, the interface and the deployment.

How the pieces fit

  • The agent. A scheduled task fires each evening into a fresh session with no memory of the last one, so all of its context comes from a standing brief in the repo. It classifies replies from the usual applicant tracking systems into pipeline moves, searches Seek, Indeed and GradConnection through a real browser because plain fetches get a 403, and reads every ad before recording it. Its output is an updated seed file rather than a live write, and a push notification tells me what changed.
  • The sync bridge. The agent runs in a sandbox whose network policy blocks Supabase, so rather than working around that I split the pipeline at the boundary. The agent produces the seed file; a nightly Node script pushes it the last hop, logging to a file, because a scheduled job that fails silently is worse than no job at all.
  • The app. React 18 and TypeScript in strict mode, built with Vite, styled with Tailwind and deployed on Netlify. It reads from Supabase Postgres and subscribes to realtime changes, so an edit on my phone shows up on my laptop, and it falls back to local storage when no database is configured, which keeps it working offline. The Today view works out the action queue in the browser, and writes are optimistic, so the interface updates straight away and reconciles with the server afterwards. Every push runs the CI pipeline on GitHub Actions: typecheck, then the unit tests, then a production build. If any of the three fails, nothing deploys.

Outcome

I use it every day, and the pipeline keeps itself current instead of me maintaining it by hand. The more useful outcome was what building it forced me to learn: row level security, realtime sync, a storage layer that degrades cleanly to offline, and where the sensible boundary sits between what a scheduled agent should decide and what I should.

Thesis

Honours research

Completed Honours Thesis · Deakin University · 2026

Monitoring the Health & Reliability of Remote Autonomous Systems

My completed Honours thesis designs, builds and evaluates a lightweight, Prometheus-based framework for monitoring remote autonomous systems, such as drones and robots, in real time, so faults can be caught early without relying on cloud infrastructure or pre-labelled fault data.

System monitoring

Collecting and tracking live health metrics from remote systems as they operate.

Fault detection

Spotting failures and anomalies early, before they turn into bigger problems.

Telemetry analysis

Making sense of streamed sensor and status data to understand system behaviour.

Approach & tools

A custom Python telemetry exporter feeding Prometheus and Grafana, evaluated on a public drone dataset and on a physical DJI Tello drone.

Key result

Detected 9 of 9 induced faults on the live drone at a median 6.0 s latency, with no sustained false alerts across 13.2 min of normal flight.
